Rate Limiting: Algorithms, Design, and Trade-offs

A deep dive into the four core rate limiting algorithms — Token Bucket, Leaky Bucket, Sliding Window, and Fixed Window — with animated diagrams, worked examples, and real-world use cases.

What is Rate Limiting?

Rate limiting is a technique to control the number of requests a client can make to an API within a specified time period. It's a form of throttling — a protective mechanism that enforces a maximum quota per client.

Instead of allowing unlimited requests, a rate limiter answers these questions:

  • "Can this request proceed?" — Yes, the quota still has remaining capacity
  • "Should this request be blocked?" — Yes, the quota is exhausted and must wait for the refill period
💡 Example: An API might allow 100 requests per hour per user. The 101st request is rejected with an HTTP 429 Too Many Requests status.

Rate Limiting Algorithms

1. Token Bucket Algorithm

The token bucket is the most popular algorithm, used by AWS API Gateway, Stripe, and GitHub. It models a bucket that fills with tokens over time.

How It Works

  1. A bucket has a fixed capacity (e.g., 100 tokens)
  2. Tokens are refilled at a constant rate (e.g., 100 tokens per hour)
  3. Each request consumes 1 token
  4. If the bucket has tokens, the request succeeds and one token is decremented
  5. If the bucket is empty, the request is rejected until tokens refill

2. Leaky Bucket Algorithm

The leaky bucket models a bucket with a hole in the bottom. Requests queue up and leak out at a constant rate regardless of how fast they arrive.

How It Works

  1. Requests are enqueued into a bucket with fixed capacity
  2. Requests are processed at a constant rate (e.g., 2 req/sec)
  3. If the bucket is full, new requests are rejected immediately
  4. Otherwise, requests wait in line until the "leak" processes them

3. Sliding Window Counter Algorithm

The sliding window counts requests in a moving time window that trails behind the current moment. Old requests slide out one by one as time passes.

How It Works

  1. Define a time window (e.g., 1 hour trailing)
  2. Count all requests within the current window [now - 3600s, now]
  3. If count ≥ limit, reject; otherwise accept
  4. As time progresses, old requests slide out of the window one by one

4. Fixed Window Counter Algorithm

The fixed window is the simplest approach: divide time into fixed buckets and count requests per bucket. When the interval boundary passes, the counter resets to zero.

How It Works

  1. Divide time into fixed intervals (e.g., 1-hour buckets)
  2. Count requests in the current interval
  3. If count ≥ limit, reject; otherwise accept
  4. When the interval boundary passes, reset counter to 0

Real-World Examples

Token Bucket

GitHub API Rate Limits

  • Unauthenticated: 60 requests/hour
  • Authenticated: 5,000 requests/hour per user
  • Premium: Unlimited

Each request consumes 1 token. The bucket refills continuously over the hour.

Why token bucket? Power users can burst all 5,000 requests at once when needed. The smooth refill prevents cliff effects that would frustrate developers, and each user has their own separate bucket making it fair.

Sliding Window

Payment Gateway (Stripe)

  • Track requests in a moving 1-second window
  • Limit: 100 requests/second per API key

Why sliding window? Payments require precision timing — a fixed window reset could produce a burst that causes double-charges or race conditions. High accuracy is required to maintain compliance and trust.

Leaky Bucket

CDN Traffic Shaping

  • Incoming requests are queued
  • Egress bandwidth is constant (e.g., 1 Mbps per client)

Why leaky bucket? Traffic spikes must not overwhelm the origin server. A smooth, constant output rate makes infrastructure planning predictable and keeps origin connection pools manageable.

Fixed Window

DDoS Mitigation

  • Track requests per IP per minute
  • Block if more than 10,000 requests/minute

Why fixed window? In an emergency deployment, speed and simplicity matter. The double-spend boundary issue is an acceptable trade-off because DDoS protection is already an imperfect defense at this layer.

Distributed Rate Limiting

Each server performs an atomic compare-and-swap (CAS) Lua script in Redis:

  1. Read current token count
  2. If count > 0: decrement and confirm — request proceeds
  3. If count = 0: abort — return 429

Only one CAS operation can complete at a time per key, keeping state consistent across all servers.

3. Response Behavior

When a rate limit is exceeded, APIs typically respond with:

HTTP 429 Too Many Requests

{
  "error": "Too Many Requests",
  "message": "Rate limit exceeded",
  "retry_after": 3600
}

X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1704067200
Retry-After: 3600
  • Retry-After — tells the client how many seconds to wait before retrying
  • X-RateLimit-Remaining — shows how many tokens remain in the current window
  • X-RateLimit-Reset — Unix timestamp when the next refill occurs
